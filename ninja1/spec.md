# NINJA1 — wire format

A NINJA1 patch rebuilds a target file from a source by copying the source and overwriting named regions with literal bytes. It carries the source's CRC32, MD5, and SHA1 so an applier can confirm it has the right file, and a ROM-type tag that selects a per-platform normalization. The format comes in four shapes — binary or textual, each either plain or compressed — under the shared file extension `.RUP`.

This writeup is drawn from the format's own spec sheet (`upstream/ninja1-filespec10.txt`) and its only implementation, Derrick Sobodash's `ninja.php` (`upstream/ninja-1.01php.tar.gz`, 2004). Where the two disagree, the implementation is what the patches in the wild were made by, so it is what this document follows — and each disagreement becomes an entry in `questions.md`. Points the spec sheet leaves open are deferred there too.

## Identity

Every NINJA1 patch opens with an eight-byte preamble: the five ASCII bytes `NINJA`, then the version byte `1` (ASCII `0x31`), then two bytes naming the subformat.

```
┌─────────┬─────┬────────────┐
│  NINJA  │  1  │  subformat │
│   (5)   │ (1) │    (2)     │
└─────────┴─────┴────────────┘
```

The four subformats, as their full eight-byte preambles:

| Preamble bytes | Subformat |
|----------------|-----------|
| `NINJA1B ` (`…42 20`) | binary |
| `NINJA1BZ` (`…42 5A`) | binary, compressed |
| `NINJA1T\n` (`…54 0A`) | textual |
| `NINJA1TZ` (`…54 5A`) | textual, compressed |

In a compressed subformat, everything after the eight-byte preamble is a single zlib stream; inflating it yields the same body a plain patch of that kind carries directly. Compression is otherwise invisible to the format — the body below is identical whether it arrived raw or inflated.

## Binary body

```
┌──────────┬─────────┬───────┬────────┬────────────┬───────┐
│ ROM type │  CRC32  │  MD5  │  SHA1  │ records... │  EOF  │
│   (1)    │   (4)   │ (16)  │  (20)  │    (*)     │  (4)  │
└──────────┴─────────┴───────┴────────┴────────────┴───────┘
```

The header is a one-byte ROM type (see [ROM types](#rom-types)), then the source's CRC32 as four big-endian bytes, its MD5 as sixteen bytes, and its SHA1 as twenty bytes. A field that is all zero means "no value recorded" — the applier skips that check rather than reading a real hash of zero.

Each record names an output offset and the bytes to write there:

```
┌────────┬────────┬────────┬────────┬──────────┐
│ offlen │ offset │ lenlen │ length │ payload  │
│  (1)   │(offlen)│  (1)   │(lenlen)│ (length) │
└────────┴────────┴────────┴────────┴──────────┘
```

`offlen` is a single byte giving the width of the `offset` field; `offset` is that many big-endian bytes. `lenlen` and `length` describe the payload width the same way. The `payload` is `length` bytes written literally over the target at `offset` — a raw overwrite, not an XOR and not run-length-encoded. Both `offset` and `length` are minimal-width: the encoder emits the fewest bytes that hold the value.

The record stream ends with a trailer of four bytes — a `0x03` followed by the ASCII `EOF`:

```
┌──────┬──────────┐
│ 0x03 │  "EOF"   │
│ (1)  │   (3)    │
└──────┴──────────┘
```

This trailer is shaped exactly like the front of a record: a width byte of `3`, then three bytes. An applier reads `offlen`, reads that many bytes, and stops if they are `EOF`. That equivalence is deliberate on the wire but has a consequence — a record whose offset is `0x454F46` minimally encodes to the three bytes `45 4F 46`, which *are* `EOF`, so its header is indistinguishable from the trailer. See the sentinel-collision question.

## Textual body

The textual body is lines of ASCII, separated by `\n`. A line whose first character is `#` is a comment and is ignored; the reference maker writes two comment lines (a "generated by" banner and a format note) ahead of the content.

The first non-comment line is the header — a ROM-type *name* and up to three checksums, separated by spaces:

```
snes a1b2c3d4 00112233445566778899aabbccddeeff 00112233445566778899aabbccddeeff00112233
```

The ROM type is a name here (`raw`, `snes`, `gba`, …) rather than the binary form's number. Each checksum is a hex string, or the word `unk` to record no value and skip that check.

Every non-comment line after the header is a record — a hex offset, a space, then the payload as hex:

```
100 aabbcc
```

writes the three bytes `0xAA 0xBB 0xCC` at offset `0x100`. As in the binary body, the payload is a literal overwrite.

## Records write literal bytes

Applying a NINJA1 patch copies the source, then overwrites each record's region with its payload. Because records carry absolute offsets and literal bytes, a patch can only rewrite existing bytes or extend the file: the maker grows a longer target by emitting a final record covering the extra tail. There is no truncation directive and no output-size field, so the target is never shorter than the source.

The format does not state that records must arrive in offset order, nor that their regions must be disjoint. What an applier does with unsorted or overlapping records is left open — see the record-order question.

## Source verification

The three hashes let an applier confirm the file it was handed is the one the patch was built against. A binary patch skips a check when its field is all zero; a textual patch skips one when its slot holds `unk`. A patch may carry all three, some, or none.

For a large source — more than `0x1E00000` bytes (30 MiB) — the hashes are computed not over the whole file but over a sample, so a patcher need not read gigabytes to validate one. The sample is the first `0x1400000` bytes (20 MiB), then the last `0xA00000` bytes (10 MiB), then the source's length written as a decimal ASCII string, concatenated in that order. All three hashes run over that same sample. An applier has to reproduce it exactly to verify against a large-file patch.

## ROM types

The ROM-type field is both a label and a selector for normalization — stripping copier headers and deinterleaving so that one patch fits several dumps of a game. Only three types carry a procedure; the rest are handled as raw bytes.

| # | Name | # | Name | # | Name |
|---|------|---|------|---|------|
| 0 | raw | 6 | gba | 12 | pce |
| 1 | nes | 7 | ngp | 13 | ws |
| 2 | snes | 8 | ngpc | 14 | wsc |
| 3 | n64 | 9 | sms | 15 | lynx |
| 4 | gb | 10 | gg | 16 | jag |
| 5 | gbc | 11 | mega | 17 | gp32 |

`mega` is the Sega Genesis / Mega Drive. The three types with a normalization procedure are `snes`, `mega`, and `gb`; the per-platform procedures, and slap's dispositions on them, live in [`rom-normalization.md`](rom-normalization.md).

## What the format doesn't specify

The layout above is the spec. What it leaves open — in what order records apply and what happens when they overlap, what an applier does with a binary stream that never reaches its `EOF` trailer, how to read a record whose offset collides with that trailer, what any bytes after the trailer mean, and how wide an `offset` or `length` field is allowed to grow — is either implementation convention or genuinely undecided. Those, together with the handful of places where the spec sheet and `ninja.php` disagree outright, are answered in [`questions.md`](questions.md).
